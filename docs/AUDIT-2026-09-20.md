# Repository exposure and functional audit · 2026-09-20

## Scope and conclusion

Reviewed the public `Fiouri/privacy-suite` repository at `a58fd74a3a0cb48b6888fb0486d96190df54eaba`, its complete published history, public CI outputs, and https://fiouri-privacy-suite.pages.dev/.

No exposed credentials, private keys, personal email addresses, user files, or unintended private configuration were found in the inspected surfaces. No application defect was reproduced in the tested functionality. This is an engineering review and automated verification, not an independent security certification or proof that undiscovered defects cannot exist.

## Public exposure review

- Gitleaks v8.30.1 from its official release, verified against its published SHA-256 checksum: no findings across all four existing commits, commit messages, all three CI job logs, and all three downloadable build artifacts.
- Supplementary inspection covered 39 tracked files and 48 distinct historical text blobs: no personal filesystem paths, Cloudflare account identifiers, private email addresses, credential/configuration files, source maps, databases, or personal downloads found.
- Commit author/committer email addresses use GitHub `noreply` addresses. The public username, MIT license, app URL, source code, and synthetic fixture passwords are expected public information for this open-source project.
- GitHub Secret Scanning is enabled and showed zero open and zero closed alerts.
- One public branch (`main`); no tags, releases, issues, pull requests, issue/commit comments, or forks at inspection time. The Wiki has no pages; Discussions are disabled.
- Each CI artifact contains only nine build files: HTML, JS, CSS, icons, manifest, service worker, and hosting headers. No failed-test artifact existed at inspection time. Browser tests use fresh contexts and synthetic data only.
- Production probes for `.env`, `.git/config`, source files, `package.json`, `_headers`, and source maps returned only the SPA HTML fallback, not the requested sensitive file. A 200 fallback response is not evidence that those files are exposed.
- Real HTTPS responses have restrictive CSP and security headers, no `Set-Cookie`, and disabled NEL/reporting policies. The app source has no upload, tracker, analytics, user-data persistence, or third-party runtime API calls. The worker fetches only application assets from the same origin.
- `npm audit --audit-level=low`: zero reported vulnerabilities, including development dependencies, at audit time.

## Test coverage added

- Independently authenticated malformed metadata: invalid UTF-8, JSON, types, field limits, and malicious length prefixes.
- Actual 50 MiB binary encryption/decryption with SHA-256 comparison; rejection at 50 MiB plus one byte.
- Independent Node AES-GCM decryption of app-format ciphertext, plus existing independent-writer interoperability.
- Appended/truncated ciphertext and maximum-length Unicode passwords.
- All 15 nonempty password group combinations at 12 and 128 characters.
- Password confirmation, show/hide, clear, tool switching, and disposal of prior visible results.
- Malicious-looking filenames rendered as text; damaged ciphertext rejected without a download.
- Drag-and-drop, repeated selection of the same file, and privacy-panel controls.
- Secure-crypto absence fails closed; clipboard rejection presents a usable fallback. Real copy/readback is tested in an isolated Chromium context.
- Online and offline download round trips compare real recovered bytes, including after a service-worker reload.

The download test harness previously made a second filesystem copy that intermittently failed with Windows `EPERM`. Chromium's stream wrapper also returned zero bytes while the completed file on disk contained 127 bytes. The tests now read the completed browser download directly with bounded filesystem retries. They still assert successful downloads, expected filenames, ciphertext privacy, wrong-password rejection, and exact plaintext recovery. Application behavior was not changed to work around the test environment.

## Remaining hardening observations

These are configuration/maintenance gaps, not detected data leaks:

- Dependabot alerts are disabled; the existing CI dependency audit only runs when CI runs.
- Private vulnerability reporting is disabled. `SECURITY.md` already warns against posting exploit details publicly and explains this limitation.
- `main` is not protected. Contributors cannot push without repository permission, but an authorized maintainer can bypass a pull request and CI review.
- GitHub Actions are referenced by major-version tags rather than immutable commit SHAs.

No account permissions, branch protection, paid services, or destructive history rewrites were changed as part of this audit.

## Verification limits

Physical Android/iOS PWA installation, memory pressure on low-end devices, browser extensions, and operating-system clipboard sync were not tested. Hosted WebKit offline emulation is skipped on Windows; WebKit offline behavior is covered separately using a disconnected local server. Automated real-clipboard permission tests are Chromium-only; clipboard-denial UI is tested in all three engines. Host-controlled access logs and infrastructure internals are outside the app's control. Other repositories and profile history outside this project were not audited.
